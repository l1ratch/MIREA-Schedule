# 🤝 Руководство контрибьютора MIREA Schedule

Привет! Мы рады любому вкладу в развитие приложения **MIREA Schedule**. Этот документ описывает правила командной разработки, стандарты ведения веток, сборки тестовых версий и создания Pull Request, чтобы совместная работа была удобной, прозрачной и предсказуемой.

---

## 🧭 1. Основные принципы работы над проектом

1. **Одна задача — одна ветка:** Не смешивайте в одной ветке разные фичи или правки, не относящиеся к теме.
2. **Всегда проверяйте на устройстве:** Перед созданием PR обязательно соберите тестовый APK или IPA через наш CI и проверьте работу на реальном телефоне.
3. **Безопасность:** Никогда не добавляйте в коммиты персональные токены, пароли или секреты.
4. **Не раздувайте зависимости:** Проект придерживается простоты (YAGNI). Предпочитайте стандартные возможности Kotlin Multiplatform и Compose сторонним тяжелым библиотекам.

---

## 🌿 2. Правила работы с ветками (Branching Strategy)

### 2.1. Откуда создавать ветку
Новая ветка **всегда создается от актуального состояния ветки `main`**:
```bash
git checkout main
git pull origin main
git checkout -b <тип>/<краткое-описание>
```

### 2.2. Конвенция именования веток
Имя ветки должно отражать суть задачи и следовать формату:  
`<тип>/<описание-через-дефис>`

| Префикс | Когда использовать | Примеры хороших названий |
| :--- | :--- | :--- |
| `feat/` | Новая функциональность, экраны, виджеты | `feat/widget-next-lesson`, `feat/stromynka-floor-5` |
| `fix/` | Исправление багов, опечаток, вылетов | `fix/android-map-zoom`, `fix/room-card-position` |
| `refactor/` | Изменение структуры кода без смены логики | `refactor/schedule-repository`, `refactor/svg-loader` |
| `docs/` | Правки документации и инструкций | `docs/contributing-guide`, `docs/api-readme` |
| `perf/` | Оптимизация производительности | `perf/compose-lazy-column`, `perf/map-caching` |

❌ **Как называть ветки НЕЛЬЗЯ:**
* `fix_p_m`, `patch1`, `test`, `temp`, `my-branch`, `work` — по таким именам невозможно понять, кто и что менял, а также такие имена затрудняют автоматический аудит.
* Не используйте заглавные буквы, пробелы и нижние подчеркивания в именах веток (используйте kebab-case: `feat/awesome-feature`).

## 🛠️ 3. Стандарты кода и работы с файлами

### 3.1. Kotlin Multiplatform & Compose
* Вся общая логика, экраны и модели живут в `shared/src/commonMain/kotlin`.
* **Запрещен `runBlocking`** на основном UI-потоке — это приводит к подвисаниям интерфейса. Используйте корутины и правильные диспетчеры (`Dispatchers.Default` для расчетов, `Dispatchers.IO` для ввода-вывода).
* Сохраняйте состояние Compose-компонентов через `remember` / `rememberSaveable` и избегайте лишних рекомпозиций.

### 3.2. Векторные карты (SVG)
Файлы карт находятся в `shared/.../files/maps/<campus>/`. При редактировании планов этажей:
* **Валидность XML:** SVG обязан быть валидным XML без незакрытых тегов.
* **Структура слоев:** Сохраняйте корневые группы `<g id="walls">`, `<g id="room-polygons">`, `<g id="room-labels">`, `<g id="markers">`.
* **Объединение полигонов:** Если аудитория большая, не нарезайте её на несколько смежных полигонов — объединяйте их в один контур, чтобы при клике подсвечивалась вся аудитория целиком.
* **Маркеры этажей:** Лестницы должны содержать атрибут `aria-label="Лестница на Этаж N"`, так как скрипт переключения этажей ориентируется на это поле.

## 🧪 4. Как собрать и протестировать приложение в своей ветке

Мы настроили изолированный тестовый сборщик, который собирает APK и IPA **без изменения релизов и без накрутки номеров версий**:

1. Отправьте свою ветку на GitHub:
   ```bash
   git push -u origin <ваша-ветка>
   ```
2. Откройте репозиторий на GitHub и перейдите во вкладку **Actions**.
3. В списке слева выберите воркфлоу **`🧪 Contributor Test Build (APK & IPA)`**.
4. Справа нажмите кнопку **Run workflow**:
   * В поле **Use workflow from** оставьте `main` (или выберите свою ветку, если в неё уже подтянут `main`).
   * В поле **Ветка для сборки** введите название вашей ветки (например: `fix/room-card-position`).
   * Отметьте нужные платформы (`Build Android APK` / `Build iOS IPA`).
   * Нажмите зеленую кнопку **Run workflow**.
5. Дождитесь завершения сборки (~2 минуты для Android, ~8 минут для iOS).
6. Прокрутите страницу запуска в самый низ до секции **Artifacts** и скачайте установочный пакет:
   * **`Schedule-MIREA-APK`** — тестовый Android-файл.
   * **`Schedule-MIREA-IPA`** — тестовый iOS-файл (для установки через TrollStore, Scarlet, Sideloadly и др.).
7. Проверьте поведение на реальном смартфоне.

## 🔍 5. Автоматический аудит ветки перед мерджем

Перед открытием Pull Request запустите нашего робота-аудитора:
1. Перейдите во вкладку **Actions** ➔ воркфлоу **`🔍 Review Branch vs Main`**.
2. Нажмите **Run workflow**, введите имя вашей ветки и запустите проверку.
3. Бот:
   * Проверит различия относительно актуального `main`.
   * Выявит возможные архитектурные риски (блокировки потоков, потенциальные утечки).
   * Сформирует список затронутых модулей и чеклист проверки.
   * (При включенной опции) Может автоматически создать или обновить Pull Request с готовым описанием!

---

## 🚀 6. Создание Pull Request (PR)

Когда изменения протестированы на телефоне и аудит пройден:
1. Откройте **Pull requests** ➔ **New pull request**.
2. В качестве **base** выберите строго **`main`**, а в качестве **compare** — вашу ветку.
3. **Заголовок PR:** Кратко опишите суть по Conventional Commits (например: `fix(map): move room info card below campus header`).
4. **Описание PR:**
   * **Что сделано:** Кратко по пунктам перечислите изменения.
   * **Зачем:** Какую проблему решает или что улучшает данный PR.
   * **Результаты тестирования:** Укажите, на каких устройствах и платформах проверялась сборка.
5. Дождитесь ревью maintainer'а. При необходимости внесите правки новыми коммитами в ту же ветку — PR обновится автоматически.

---

## 📦 7. Как происходят официальные релизы

* Контрибьюторам **не нужно** вручную менять номера сборок или выпускать релизы.
* Когда maintainer принимает ваш PR и мерджит его в ветку `main`, автоматически запускается официальный релизный сборщик **`🚀 Build & Release Mobile (Main Only)`**.
* Он самостоятельно инкрементирует номер сборки, публикует GitHub Release и обновляет ленту версий `version.json` на `gh-pages` для автообновлений в приложении.
